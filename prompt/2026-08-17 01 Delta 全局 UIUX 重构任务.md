# Delta 全局 UI/UX 重构任务

> 本任务用于直接在 **Delta 当前真实代码库**中完成一次全局 UI/UX 审计、设计系统统一、真实代码重构与验证。
> 不是设计讨论，不是 Demo 制作，不是截图微调任务。
>
> **v1.3 变更说明**：在 v1.2 基础上修复三处收尾阶段的边界空白——
> 1) 0.1 节补充"基线快照"用途，让 Changed Files 的口径在无 checkpoint commit 时依然可判定；
> 2) 新增 10.5 节，区分"快照过期"与"逻辑失败"；
> 3) 新增 12.1 节，明确 Build FAIL 时如实报告、不得为了报告好看静默缩小任务范围。
> 其余章节内容与 v1.2 一致。

# 0. 最高优先级：执行边界与冲突规则

以下规则优先级高于全文其他任何设计要求。

当不同要求发生冲突时，按以下顺序判断：

```text
P0  仓库与用户现有代码安全
P1  现有功能、业务逻辑与数据行为不回归
P2  构建、类型、测试与 Accessibility
P3  本任务冻结的 Design System
P4  局部视觉偏好与审美微调
```

任何时候都不得为了满足低优先级要求破坏高优先级要求。

---

## 0.1 仓库安全【v1.3：补充基线快照用途】

正式审计和修改前，必须先确认并**记录为基线快照**：

```text
当前 branch：
git status：
git diff（若有未提交修改，完整保存这份 diff 或等价记录）：
是否存在用户已有未提交修改：
是否存在 untracked files（列出具体路径）：
```

这份基线快照的用途：

> **在没有强制 checkpoint commit（见 0.4）的前提下，任务结束时用它来区分"哪些改动是本任务产生的"与"哪些改动在任务开始前就已存在"。**

具体规则：

```text
最终 Changed Files 清单
  = 任务结束时的工作区差异
  − 基线快照中已经存在的未提交改动路径
```

不依赖 Git commit 历史来判断归属（因为 0.4 节规定默认不强制 commit）。若某个文件在基线中已经处于修改状态，且本任务又对它做了改动，需要在报告中注明"该文件基线已有修改，本任务在此基础上叠加了 UI 相关改动"，不要笼统归为"本任务修改"或完全略过。

如果工作区已经存在用户修改：

- 不覆盖；
- 不回滚；
- 不删除；
- 不格式化掉；
- 不通过 reset / checkout 等方式恢复；
- 不把这些修改误认为本任务产生；
- 不擅自将其混入 checkpoint commit。

禁止为了获得"干净工作区"执行类似：

```bash
git reset --hard
git checkout .
git restore .
git clean -fd
```

除非这些操作明确只针对**本任务刚刚产生且确认需要撤销的文件**。

## 0.4 Git checkpoint 规则

**不要机械地每个 Phase 自动 commit。**

默认原则：

1. 无代码变更的 Phase 不创建空 commit；
2. 已存在用户未提交修改时，不擅自创建包含其内容的 commit；
3. 每个主要实施阶段结束后，通过 `git status` / `git diff` 确认本阶段范围；
4. 只有项目已有规则明确允许自动本地 checkpoint，且能够保证 commit 只包含本任务修改时，才允许建立 checkpoint commit；
5. 否则保持工作区修改即可，不为了"满足流程"污染 Git history。

不得 push、merge、rebase 或修改远端仓库。

```text

3. Spacing
```

# 5. 冻结视觉系统

## 5.1 核心哲学

# Whitespace is the divider

建立层级的优先顺序：

```text
留白
→ 位置
→ 字号
→ 字重
→ 文字颜色
→ 背景差异
→ Border
→ Shadow
```

能通过前五项建立信息层级时：

> 不增加额外容器。

---

## 5.2 卡片原则

禁止：

```text
卡片套卡片
每个设置项一个卡片
每个 Agent Step 一个卡片
每个文件一个卡片
每个状态一个卡片
Sidebar Item 卡片化
Context 卡片墙
```

普通内容优先：

```text
标题

正文 / 内容

状态

下一节
```

而不是给每一块信息套 `Surface / Card / Panel`。

允许明确容器的场景：

```text
Composer
Code Block
Diff
Artifact
Dialog
Popover
Toast
Error
Warning
Approval
独立滚动 Pane
必须形成点击目标的控件
```

允许容器也必须：

> **轻背景 + 小圆角 + 少边框 + 少阴影。**

## 6.3 品牌颜色原则

Delta UI 的品牌定义是：

> **Gray Blue Brand System**

而不是：

> 蓝色应用。

主要交互基准：

```text
#4A6572
```

Logo 可继续保留更鲜明的 Delta Blue，例如：

```text
#2563EB
```

但是：

```text
Logo = 品牌识别
UI = 长时间工作舒适度
```

不要让整个 App 跟随 Logo 大面积变成高饱和蓝色。

## 6.4 Agent Semantic Colors

映射：

```text
Planning / Running / Info

Done / Success
→ Moss Green

```

Light 基准：


# 7. Typography / Density / Interaction

## 7.1 Typography

优先使用系统字体。

```css
font-family:
  -apple-system,
  BlinkMacSystemFont,
  "SF Pro Text",
  "PingFang SC",
  "Segoe UI",
  "Microsoft YaHei",
  sans-serif;
```

不得新增强制字体依赖。

参考：

```text
Page title          24–28px / 650
App / Window title  16–18px / 650
Section title       13–14px / 600
Body                14–15px / 400
Secondary           12–13px / 400
Metadata            11–12px / 400
```

避免大面积：

```text
700 / 800 / 900
```

---

## 7.2 长文本

Agent 输出、报告、说明等长期阅读内容：

```css
max-width: 68ch;
font-size: 14px ~ 15px;
line-height: 1.6 ~ 1.7;
```

大窗口：

> 增加外围留白。

不要：

> 无限增加正文行宽。

---

## 7.3 Radius

```text
Small control   6–8px
Button          8–10px
Input           10–12px
Code            8–10px
Popover         10–12px
Dialog          14–16px
```

禁止 20px+ Radius 泛滥。

禁止大量 Squircle。

---

## 7.4 Shadow

普通内容：

```text
shadow: none
```

仅允许主要用于：

```text
Composer
Dialog
Popover
Tooltip
Floating Layer
```

参考：

```css
/* Light */
box-shadow: 0 8px 24px rgba(40,50,60,.07);

/* Dark */
box-shadow: 0 10px 28px rgba(0,0,0,.24);
```

---

## 7.5 Border

Border 不是默认结构工具。

普通内容优先不用 Border。

允许：

```text
Input
Dialog
Table
Popover
特殊 Control
必要 Pane Boundary
```

Hairline 可以很弱。

但需要被用户识别的：

```text
Input Boundary
Focus Indicator
重要 Interactive Boundary
重要 Icon
```

不能因为追求"轻"而失去可辨识性。

---

## 7.6 Hover

主要通过：

> **Background hierarchy change**

而不是所有内容变成 Accent。

Light 可优先：

```css
background: var(--brand-50);
```

Dark 可优先：

```css
background: var(--brand-100);
```

仅以下内容应明显使用 Accent：

```text
Link
Current Selection
Primary Action
关键 Active State
```

---

## 7.7 Animation

统一：

```text
120–180ms
```

参考：

```css
transition:
  background-color 140ms ease,
  color 140ms ease,
  border-color 140ms ease,
  opacity 140ms ease;
```

禁止：

```text
Card Hover Lift
大 Scale
Neon Glow
呼吸灯
夸张 Spring
大面积动态背景
```

必须尊重：

```css
@media (prefers-reduced-motion: reduce)
```

---

## 7.8 Focus

键盘 Focus 必须存在。

不可简单删除：

```css
outline: none;
```

除非已有等价或更清晰的 focus indicator。

可参考：

```css
outline: 2px solid
  color-mix(in srgb, var(--focus) 40%, transparent);
```

实际实现必须在 Phase 8 验证可辨识度。

---

## 7.9 Disabled

Disabled 可以低于普通正文对比度，但必须：

- 明显不可操作；
- 与正常状态清楚区分；
- 不能完全融入背景。

禁止粗暴使用：

```css
opacity: .25;
```

作用于整个复杂组件。

---

## 7.10 Selection

Light：

```css
background: rgba(74,101,114,.12);
```

Dark：

```css
background: rgba(132,157,172,.15);
```

---

## 7.11 Scrollbar

保持低视觉权重。

大约：

```text
6px
```

不要常驻明显轨道。

## 8.2 Sidebar

目标：

> **安静的 Thread Navigation**

规则：

- 无卡片墙；
- 默认无明显 border；
- 默认无 shadow；
- 不堆图标；
- Hover 使用低对比背景变化；
- Active 使用轻灰蓝 Surface；
- 状态优先使用小圆点；
- Active 不使用大块高饱和 Accent。

Sidebar 应明显存在，但不能和主工作区竞争。


不要：

```text

厚 Border
高 Shadow
大量按钮
高饱和背景
```

# 10. Accessibility 验证

Accessibility 不允许靠目测宣称通过。

## 10.1 一次性 Contrast Audit

Phase 8 使用一次性 Node 或 Python 脚本，对实际生产颜色计算：

```text
sRGB
→ Linear RGB
→ Relative Luminance
→ Contrast Ratio
```

公式：

```text
(Llighter + 0.05) / (Ldarker + 0.05)
```

输出至少包含：

```text
Token / Element
Foreground
Background
Contrast
Threshold
PASS / FAIL
```

如果颜色包含：

```text
rgba()
opacity
color-mix()
透明 Overlay
```

不能直接拿声明值计算。

必须先按照实际背景进行颜色合成，得到最终渲染 RGB，再计算对比度。

脚本属于一次性验证工具：

> 结果进入最终报告后删除。

不得留下：

```text
audit-temp.js
test-color.js
contrast-final-final.py
tmp-ui-test.*
```

## 10.5 快照测试的归类【v1.3 新增】

大规模 UI 重构必然导致项目里已有的 snapshot test / 视觉 diff test 大批"失败"。这是**预期结果**，不是自动等同于 bug。执行时必须区分两类失败，并分别处理：

```text
类型 A：结构性过期
  DOM 结构、class 名、样式值因本次重构改变，
  测试逻辑本身没有问题，只是快照内容需要更新。
  → 重新生成快照（update snapshot），
    并在最终报告的 Build/Test 部分注明
    "以下快照因视觉重构预期性更新："，列出受影响的测试文件。

类型 B：逻辑性失败
  失败原因不是快照内容变化，而是渲染报错、
  组件行为变化、断言的业务逻辑本身被破坏。
  → 必须在当前 Phase 内定位并修复，
    不得当作"预期的视觉噪音"忽略。
```

不确定属于哪一类时，先查看具体 diff 内容再判断，不要凭失败数量批量猜测。全部重新生成快照而不看 diff、或者全部忽略当作噪音，都是不允许的处理方式。

# 12. 验证节奏与防死循环

不要每修改几个 CSS 就跑完整构建。

```text

→ typecheck

Phase 4 完成
→ typecheck

Phase 6 完成
→ typecheck

Phase 7 完成
→ typecheck

Phase 8
→ Accessibility + Visual QA

Phase 9
→ lint + unit + e2e + production build
```

项目不存在的命令：

> `NOT AVAILABLE`

不得自行新增无意义框架来制造一个 PASS。

如果 typecheck 失败：

> 在当前阶段解决本任务引入的问题后再继续。

如果发现失败明显是执行前就存在的 unrelated issue：

> 尽可能确认并记录，不扩大任务去重构 unrelated 模块。

## 12.1 Production Build 失败时的收尾规则【v1.3 新增】

如果 Phase 9 的 production build 最终仍然 FAIL，且原因不是本任务范围内能合理修复的问题（例如暴露了 unrelated 的既有构建问题）：

```text
必须：
  如实在最终报告的 Build/Test 部分标注 FAIL，
  并列出失败原因、报错信息、判断依据
  （为什么认为它超出本任务范围）。

禁止：
  为了让最终报告显示 PASS，
  静默回退、精简、或撤销已经完成的 UI 改动；
  或者选择性只报告能通过的部分构建步骤，
  略去失败的部分。
```

如果失败原因确实由本任务改动引入，必须在当前阶段内修复到 build 通过为止，而不是留到最终报告里才说明。只有确认失败原因与本任务无关时，才允许保留改动并如实报告 FAIL。
