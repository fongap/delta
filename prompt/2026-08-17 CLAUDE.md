## Multi-Agent Collaboration Rules

### 1. Core Principle

Use multi-agent collaboration when it provides a **clear execution advantage**, not merely because a task can theoretically be split.

The goal is:

> **Reduce wall-clock time, improve correctness, and increase independent verification — without adding unnecessary coordination, duplicated exploration, or agent loops.**

Prefer parallelism when independent work can produce useful results concurrently.

Do **not** create agents merely to satisfy a role structure or maximize concurrency.

---

## 2. Decide the Execution Mode First

Before starting a non-trivial task, classify it as either:

- **Single-Agent**
- **Multi-Agent**

Use **Multi-Agent Mode** when at least one of the following is true:

- The task spans multiple modules or independent areas.
- Two or more meaningful workflows can proceed independently.
- Root cause is uncertain and multiple hypotheses are worth testing independently.
- Exploration, implementation, testing, or review can run concurrently.
- The change has broad architectural or regression impact.
- Independent verification would materially improve confidence.
- Parallel work is likely to reduce completion time enough to justify coordination overhead.

Use **Single-Agent Mode** when:

- The change is small and localized.
- The root cause and implementation path are already clear.
- The task is primarily configuration, copy, formatting, or a simple code edit.
- Work is inherently sequential.
- Multiple agents would need to modify the same small set of files.
- Coordination cost is likely to exceed execution benefit.
- The Lead already has enough evidence to implement safely.

**Do not use multi-agent mode solely because the task is labeled "medium" or "large".**

---

## 3. Parallelism Must Have a Purpose

Before creating agents, the Lead must be able to answer:

1. What independent question or deliverable does each agent own?
2. Can that work proceed without blocking another agent?
3. Will the result materially affect implementation, verification, or confidence?
4. Is parallel execution faster or safer than doing it directly?
5. Which files, modules, or concerns belong exclusively to each agent?

If these questions cannot be answered clearly, do not create the agent.

---

## 4. Recommended Roles

Select only the roles actually needed for the task.

| Role | Primary Responsibility | Restrictions |
|---|---|---|
| **Explorer** | Locate relevant code, trace call paths, identify dependencies, reproduce behavior, narrow root cause | Avoid implementation unless explicitly assigned |
| **Implementer** | Make the agreed code changes within a clearly defined scope | Do not expand scope without evidence |
| **Tester / Debugger** | Reproduce failures, run targeted tests, verify edge cases, diagnose remaining failures | Do not redesign unrelated production code |
| **Reviewer** | Independently inspect the final diff for correctness, regression risk, unnecessary complexity, and missed cases | Do not duplicate the implementation |

Not every task requires all four roles.

Typical patterns:

- Unclear bug → Explorer + Debugger, then Implementer.
- Clear multi-module feature → multiple scoped Implementers + Tester.
- Risky refactor → Explorer + Implementer + Reviewer.
- Small clear change → Lead only.

---

## 5. Primary Agent / Team Lead Responsibilities

The primary agent is the **Team Lead** and remains responsible for the final result.

The Lead must:

- Understand the user-visible goal before delegating.
- Decompose work into bounded tasks.
- Assign clear ownership.
- Prevent overlapping edits.
- Decide what requires parallel work and what should remain centralized.
- Integrate results.
- Resolve contradictory findings.
- Independently inspect important agent conclusions.
- Run or confirm final verification.
- Stop unnecessary investigation once sufficient evidence exists.
- Deliver the final result rather than merely reporting agent activity.

Subagents provide evidence and scoped work.

**They do not replace the Lead's judgment.**

---

## 6. File Ownership

Before parallel implementation begins, establish file or module ownership whenever practical.

Rules:

- Two agents must not edit the same file concurrently.
- Prefer ownership by module, component, or concern.
- Shared foundational files should normally be modified by the Lead or one designated Implementer.
- Other agents may inspect shared files but should not modify them unless ownership is transferred explicitly.
- If two changes converge on the same file, serialize those edits rather than allowing competing patches.

When ownership is uncertain:

> One agent implements; other agents analyze, test, or review.

---

## 7. Avoid Duplicate Exploration

Do not send multiple agents to independently read the entire repository unless independent comparison is specifically useful.

Each Explorer should receive a focused question such as:

- Trace authentication initialization.
- Find all callers of `X`.
- Reproduce the failure in module `Y`.
- Determine whether state is persisted in frontend or backend.
- Identify tests covering behavior `Z`.

Avoid vague assignments such as:

> "Explore the codebase and report anything relevant."

The Lead should share known context with subagents so they do not rediscover information already established.

---

## 8. Parallel-First, Dependency-Aware Execution

Independent work should run concurrently.

Dependent work should not.

Example:

```text
Explorer A ─┐
Explorer B ─┼─> Lead decides root cause ─> Implementer ─> verification
Debugger  ──┘
```

Do not start an Implementer before required architectural or root-cause information is available.

However, do not wait for every exploratory task if enough evidence already exists to proceed safely.

The Lead may cancel, ignore, or stop lower-value exploration once the decision is sufficiently supported.

---

## 9. Agent Budget

Use the **smallest useful team**.

Default guidance:

- Small task: **0 subagents**
- Moderate task: **1–2 subagents**
- Large independent task: **2–4 subagents**
- More than 4 agents requires a clear justification

Do not automatically use the maximum concurrency available.

Every additional agent must have a distinct expected output.

---

## 10. Investigation Budget

Exploration must converge toward a decision.

For debugging:

1. Reproduce the issue.
2. Collect evidence.
3. Form a small number of plausible hypotheses.
4. Test the highest-value hypotheses.
5. Select the best-supported root cause.
6. Implement the smallest correct fix.
7. Verify.

Do not repeatedly broaden the search after the root cause is sufficiently established.

Do not continue exploring merely because more files, logs, or edge cases exist.

### Stop exploring when:

- The failure is reproducible.
- The responsible code path is identified.
- Evidence explains the observed behavior.
- A bounded fix can be proposed.
- Additional investigation is unlikely to change the implementation decision.

---

## 11. No Agent Recursion by Default

Subagents should not independently create additional subagents unless the Lead explicitly requires it.

The Lead owns team topology.

This prevents:

- uncontrolled fan-out,
- duplicated exploration,
- excessive token use,
- unclear responsibility,
- nested coordination loops.

Prefer a shallow team structure:

```text
Lead
├── Agent A
├── Agent B
└── Agent C
```

instead of recursive agent trees.

---

## 12. Implementation Discipline

Once sufficient evidence exists:

> **Stop investigating and implement.**

Implementation should:

- Address the demonstrated root cause.
- Make the smallest coherent change that solves the task.
- Respect existing architecture and conventions.
- Avoid unrelated cleanup.
- Avoid speculative abstractions.
- Avoid rewriting working code without necessity.
- Avoid broad refactors unless they are required by the task.

If a nearby issue is discovered but is not required for the requested result, record it as a follow-up rather than silently expanding scope.

---

## 13. Failure Handling

A failed test or implementation attempt must produce **new information** before another attempt is made.

Do not repeatedly:

```text
edit → test → fail → edit → test → fail
```

without explaining why the next change should succeed.

After a failure:

1. Read the actual error.
2. Determine whether it invalidates the current hypothesis.
3. Identify the specific cause.
4. Make one evidence-based correction.
5. Re-run the narrowest relevant verification.

If the same failure persists after repeated attempts, stop changing code blindly and return to diagnosis.

---

## 14. Prevent Debugging Loops

Do not enter indefinite search/test/fix cycles.

Escalate back to the Lead when:

- Two consecutive fixes fail for the same underlying symptom.
- Evidence contradicts the current root-cause hypothesis.
- Fixing the issue appears to require expanding scope materially.
- A test failure appears unrelated to the current change.
- The agent cannot distinguish environment failure from code failure.
- Further work would be speculative.

The Lead must then reassess the hypothesis before additional modifications.

---

## 15. Testing Strategy

Verification should proceed from narrow to broad.

Preferred order:

1. Reproduce the original issue.
2. Run the nearest relevant unit/component test.
3. Run affected module tests.
4. Run broader integration/e2e tests when justified.
5. Run typecheck/lint/build as required by the repository.
6. Perform final regression review.

Do not repeatedly run the entire test suite after every small edit unless necessary.

Use targeted verification during iteration and broader verification near completion.

---

## 16. Reviewer Rules

Reviewer work is intended to provide an **independent final check**, not create another implementation cycle.

Review the actual diff and check:

- Does the change solve the stated problem?
- Is the root cause actually addressed?
- Are there obvious regressions?
- Is unnecessary complexity introduced?
- Were unrelated files changed?
- Are tests sufficient?
- Are error paths and edge cases reasonable?
- Does the implementation follow existing architecture?

Classify findings as:

- **Blocking** — must fix before delivery.
- **Non-blocking** — worth mentioning but does not prevent completion.
- **Out of scope** — record only.

Do not reopen implementation for subjective stylistic preferences unless they violate repository standards or introduce meaningful maintenance risk.

---

## 17. Completion Criteria

A task is complete when:

- The requested behavior is implemented.
- The original issue or requirement has been verified.
- Relevant tests pass.
- Required typecheck/lint/build checks pass, or failures are clearly identified as pre-existing/environmental.
- The final diff has been reviewed.
- No known blocking issue remains.

Do not continue working merely to seek theoretical perfection once the completion criteria are satisfied.

---

## 18. Stop Conditions

The Lead must terminate agent activity when:

- Required information has been obtained.
- An agent's task has already been answered by another result.
- Continued investigation has diminishing value.
- The implementation decision is already sufficiently supported.
- The requested task is complete.

Agents are tools for reaching the deliverable, not tasks that must all run to completion.

---

## 19. Communication Between Agents

Agent outputs should be concise and decision-oriented.

Prefer:

```text
Finding:
Evidence:
Affected files:
Recommended action:
Risks:
```

Avoid long narrative summaries of every command executed.

Return concrete findings, file paths, symbols, test results, and actionable recommendations.

---

## 20. Final Verification Is Centralized

Subagents may run scoped verification, but the Lead owns final verification.

Before delivery, the Lead should confirm:

- final repository state,
- changed files,
- important test results,
- unresolved failures,
- scope compliance,
- regression risk.

Never assume an agent's `"tests pass"` report is sufficient without checking the relevant final state.

---

## 21. Default Decision Heuristic

Use this order:

```text
Is the task small and clear?
    └─ Yes → Lead handles directly.

Is the task unclear or broad?
    └─ Yes → Delegate focused exploration/debugging.

Are there independent implementation areas?
    └─ Yes → Assign non-overlapping ownership and run in parallel.

Is implementation path now clear?
    └─ Yes → Stop exploration and implement.

Has implementation completed?
    └─ Yes → Run targeted verification.

Is the change important or high-risk?
    └─ Yes → Independent review.

Are completion criteria satisfied?
    └─ Yes → STOP and deliver.
```

---

## 22. Anti-Patterns

Do **not**:

- Create agents merely because parallelism is technically possible.
- Create every available role for every task.
- Have multiple agents scan the same repository without a distinct purpose.
- Let multiple agents edit the same files concurrently.
- Delegate trivial edits.
- Keep exploring after the implementation decision is clear.
- Run broad tests unnecessarily after every edit.
- Retry failed fixes without new evidence.
- Allow agents to recursively spawn teams without explicit need.
- Turn reviewer suggestions into endless polish cycles.
- Expand scope because unrelated issues were discovered.
- Rewrite working architecture while fixing a localized bug.
- Wait for low-value agents when enough evidence already exists.
- Treat agent activity as progress unless it contributes to the requested deliverable.

The governing rule is:

> **Parallelize independent uncertainty and independent work. Centralize decisions, shared-file changes, integration, and final verification. Stop when the requested result is proven complete.**
