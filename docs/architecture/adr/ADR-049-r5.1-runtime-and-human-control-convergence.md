# ADR-049: R5.1 Runtime & Human Control Convergence

## Status

Accepted — implementation complete on the R5.1 branch; final repair commit is covered by green CI and CodeQL, with merge tracked by PR #200.

## Context

R5.1 is not R6. It does not add broad new product capabilities or
mechanically expand Rust coverage. Instead, R5.1 converges two
important goals:

* **R5.1A — Runtime Correctness**: fix audit findings AF-01 through
  AF-14 that affect automation, protocol, lifecycle, side-effect,
  idempotency, and citation correctness.
* **R5.1B — Live Steering & Interaction Convergence**: let the user
  adjust or cancel the task that is already running, without opening a
  second conversation or starting a concurrent turn.

### Why R5.1 combines runtime correctness and live steering

Live steering is not a decorative UI feature. A usable implementation
must preserve single-run ownership, real cancellation, bounded
backpressure, lifecycle recovery, and side-effect correctness while a
human can still intervene.

Delta already had the correct steering primitive before R5.1:

```text
busy session user_message
        ↓
RuntimePort.steer(text)
        ↓
TurnEngine.queue_steering(text)
        ↓
next safe iteration boundary
        ↓
updated model context / execution
```

R5.1 therefore does **not** introduce a second run-control authority.
The desktop keeps the main Composer available during an active turn,
and the server routes a second plain-text message on that busy session
to the existing steering path rather than starting another turn.

Two controls are in scope now:

* **Steer** changes the direction of the current turn at the next safe
  iteration boundary. It stays in the same session/run and does not
  create a concurrent turn.
* **Cancel** interrupts the current turn through the existing runtime
  interrupt path.

**Follow-up is explicitly not exposed in R5.1.** A follow-up means
"run this after the current task finishes" and therefore needs a
separate durable queue/lifecycle contract. Presenting a second button
that actually routes to Steer would be false semantics. It can be
added later only when that distinct contract exists end-to-end.

Steering is also not retroactive. It does not promise to undo a side
effect that has already executed, nor does it pre-empt an arbitrary
in-flight tool at an unsafe point.

## Decisions

### D1: Multiplexed Runtime Protocol v16 (AF-04/05/06)

Upgrade from v15 (synchronous, single-lock, no request_id) to v16:
every request carries a `request_id`. The Rust binary dispatches
streaming commands to background threads so the main stdin loop
continues reading. The Python client uses a dedicated stdout reader
thread + per-request routing (demux).

### D2: Single Completion Owner (AF-01/AF-02)

The Scheduler is the sole finalize owner. The runner (`_run_scheduled_task`)
only executes and returns a `TaskRun`. The Scheduler calls
`TaskStore.complete_run()` exactly once — on both success and failure
paths. `complete_run` writes JSON blob AND SQL indexed columns
(`enabled`, `next_run`) in a single transaction.

### D3: Lifecycle Authority Based on Latest State (AF-03)

`open_runs()` determines recoverable-open runs from the **latest lifecycle
state**, not from whether an `interrupted` event ever appeared in history.

The final R5.1 rule is explicit:

* latest `running` or `resumed` → recoverable-open;
* latest `interrupted` → not re-listed by `open_runs()`; recovery has
  already marked that interruption and repeated sweeps remain idempotent;
* after an explicit `resumed`, the same `run_id` becomes recoverable-open
  again, so a later crash can still be recovered;
* completed / failed / skipped / cancelled / validation-failed runs remain
  closed.

This preserves the original run identity while preventing repeated stale
recovery of the same interruption.

### D4: Side-Effect Fail-Closed (AF-09)

If a side effect executed successfully but trusted persistence
(`idem_log.commit()`) fails, the tool returns `uncertain` with
`post_effect_persistence_failed`. The run stops consequential actions.
Persistence may be retried, but the side effect is NOT re-executed.

### D5: Identity Collision (AF-10)

`operation_id = hash(run_id + tool_call_id)` is immutable.
Same operation_id with different args_sha256 → `identity_collision`
error → fail-closed. No silent overwrite of committed results.

### D6: Citation Validity (AF-11)

`range_valid = None` does NOT count as a fully valid citation.
Non-lines citations (where extent verification is not yet supported)
return `reason = "range_unverified"` instead of `"valid"`.
`_count_valid_citations` only counts `reason == "valid"`.

### D7: Backpressure (AF-07)

The client uses a bounded semaphore (`_max_inflight = 64`).
When full, non-control commands raise `DeltaCoreError("overload")`.
Control commands (`request.cancel`, `ping`, `hello`) bypass the limit
so cancellation and health checks always succeed.

### D8: RunningTask Ownership (AF-12/AF-13)

The client maintains a `_running` registry: `{request_id → metadata}`.
"Who spawns owns completion." On `close()`/`_crash()`, all pending
requests and streams are fanned out with errors, and inflight slots
are released. `shutdown()` follows: graceful cancel → bounded wait →
force-close.

### D9: Tool Timeout Semantics (AF-08)

`ThreadPoolExecutor` no longer uses `with` (which blocks on
`shutdown(wait=True)`). Instead, on timeout, `shutdown(wait=False)`
abandons the thread. The status is `"uncertain"` (not `"failed"`)
because the callable may have completed in the background.

### D10: Live Steering Uses the Existing Runtime Authority

The main desktop Composer remains usable while `running == true`.
During that state it accepts plain text only and presents two honest
actions: adjust the current task, or stop it.

On the session WebSocket, if `try_mark_running(session_id)` reports
that the same session already owns an active turn, a non-retry,
unframed plain-text `user_message` is routed to `runtime.steer(text)`.
It is **not** rejected and **not** used to launch another `run_turn`.
Attachments and Skill-framed messages are not accepted as steering,
because they have independent lifecycle semantics.

`TurnEngine.queue_steering()` remains the single steering queue. The
queued text is injected when the current iteration reaches an existing
safe boundary, then the model continues with the updated context.
No parallel `RunControlChannel` registry is introduced.

### D11: Status UI Must Not Invent Runtime History

`RunStatusBar` is intentionally lightweight. It may show states the
desktop is actually observing, such as reasoning, answer streaming,
or generic execution. It does not claim a ledger-backed timeline or
expandable technical history until such events are truly wired to the
surface.

## Consequences

* The protocol version bump (15 → 16) requires both Python and Rust
  to be updated together. A mismatch is fail-closed.
* The `stream.cancel` command is replaced by `request.cancel` which
  targets `request_id` (not `stream_id`).
* Direct callers of `_run_scheduled_task` (tests, reference harness)
  no longer see `run_count` advancement — that is now the Scheduler's
  sole responsibility.
* The `open_runs()` query is slower (per-run status check) but correct.
  For typical workloads this is negligible.
* Active-turn steering reuses the existing session/runtime authority,
  so there is no second state owner to reconcile or recover.
* R5.1 intentionally ships **Steer + Cancel**, not a fake Follow-up.
  Durable follow-up remains a later, separately specified capability.
* Recovery is state-based and idempotent: `interrupted` alone is closed
  to repeated stale recovery, while an explicit `resumed` re-opens the
  same run for future crash recovery.
* Citation validity distinguishes `range_unverified` from fully `valid`,
  so unverifiable non-lines ranges do not inflate valid-citation counts.

## Follow-up

R5.1 closes the correctness and human-control foundation. It does **not** remove the persistent Python application/runtime layer.

Post-R5.1 product/runtime convergence is governed by ADR-050 and `docs/architecture/target-architecture.md`; that work belongs to R6 and must preserve the Runtime and Human Control semantics established here.
